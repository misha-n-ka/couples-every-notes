# Phase 1 — Validation Strategy

## Test Infrastructure

Документальная фаза. Используются Python со стандартной библиотекой, rg и Git только для чтения/проверки diff. Тестового фреймворка приложения, конфигурации тестов, сборки и установленного приложения нет; создавать их ради этой фазы не нужно.

- Быстрая проверка: `git diff --check -- design.md .planning/PROJECT.md .planning/REQUIREMENTS.md` и целевая текстовая проверка изменённого раздела.
- Полная проверка: внутренние ссылки, 24 REQ-ID, 20 D-ID, 5 DESIGN-ID, пересчёт всех 28 рабочих цветовых пар и смысловое чтение сценариев с позиции обоих участников.
- Никакая команда не устанавливает зависимости, не компилирует, не запускает приложение и не изменяет staging.
- Проверки наличия строк дополняют смысловую сверку; они не доказывают качество UX или серверную авторизацию.

## Sampling Rate

- После каждого значимого изменения документа — целевая проверка и diff-check, без коммитов.
- После единственной волны — весь документальный набор до передачи результата пользователю.
- Непосредственные команды и наблюдаемые признаки провала указываются в каждом задании PLAN.md.
- Локальные проверки должны завершаться примерно за 10 секунд; время просмотра внешних источников учитывается отдельно.

## Per-Task Verification Map

Один план `01-01-PLAN.md`, волна 1, три последовательные задачи. ## Wave 0 Requirements

Новых файлов тестов, фикстур, пакетов и установок не требуется. Python уже использован для документальных расчётов. Исходные данные контраста взять из текущего design.md и явно перечислить; формула и предлагаемые одноразовые команды описаны в `01-RESEARCH.md` → Validation Architecture.

## Manual-Only Verifications

- Смысл фактов об аналогах: сопоставить утверждения с указанными официальными источниками; при недоступности честно обозначить ограничение. Не выдавать поисковый фрагмент за прохождение приложения.
- Сценарии: читатель должен однозначно понять, кто видит, изменяет, удаляет и экспортирует каждый вид записи; проверить отдельно общую, личную для партнёра и приватную.
- Дата без времени не превращается в полночь с часовым поясом; события через полночь и личная копия сохраняют согласованную семантику.
- Шрифты, геометрия, расширенные токены и зона отображения сетки остаются рекомендациями, если пользователь не утверждал их отдельно.

Эти проверки выполняются по тексту документов. Браузер, пользовательские испытания, реальная проверка прав двух сессий и импорт `.ics` — не выполнены и не требуются для заявления о проверке плана.
